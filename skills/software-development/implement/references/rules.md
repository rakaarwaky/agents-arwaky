# Rules

- **Tool-call discipline** — every "launching", "spawning", "starting", or "running" statement in your prose must be backed by a `spawn_subagent` tool call in the same assistant response. Never end a turn with a content-only message that claims a subagent is being launched. See [Tool-Call Discipline (Anti-Hallucination)](../SKILL.md#tool-call-discipline-anti-hallucination).
- **Parallel-first execution** — every independent subagent launch, reviewer launch, fix cycle, and supporting read/write must be issued as a batch in a single assistant response. Only serialize when a later action consumes an earlier one's output. Never throttle independent work to save tokens.
- **One Orca worktree per run** — create a single Orca worktree named after the task slug under `workspaces/<repo-basename>/<task-slug>` with `--repo path:<repo_path> --no-parent` and no `--agent`/`--prompt`. Pass `cwd: <worktree_path>` on every fresh `spawn_subagent`. Tell the implementer not to create another worktree. The orchestrator owns commits, pushes, and PRs.
- **No permission-asking on launch** — the launch announcement is informational, not interactive. Do not append cadence-negotiation questions. Pick a default and proceed.
- **Inject personas into prompts** — prepend `implementer` for the implementer, `reviewer` for general reviewer, `security-auditor` for security specialist (from `personas/*.toml`). Do NOT pass a `persona` parameter to `spawn_subagent`. For Tests, Plan Alignment, and Simplicity specialists, do not prepend any persona — they are prompt-only.
- **Prefix `description` with a bracketed role tag** — `[implementer]`, `[reviewer]`, `[security]`, `[tests]`, `[plan]`, `[simplicity]`. The pager parses the first `[tag]` and uses it as the row label. Keep the tag on `resume_from` follow-ups.
- **resume_from on follow-ups** — never launch a fresh subagent for fix or re-review rounds. Always resume the previous one so it retains its working memory. Exception: if `resume_from` fails (subagent expired), launch a fresh one and log a warning.
- **Save every subagent_id** returned by `spawn_subagent` — needed for `resume_from` on subsequent rounds.
- **Read the review_file yourself** after each review to count open issues and decide whether to continue the loop.
- **Don't modify the implementation yourself** — all code changes go through the implementer persona subagent.
- **Explicitly tell subagents to write their output files** — include the file path and what to write in every prompt.
- **Thread the same file paths** across all rounds — never generate new paths between iterations.
- **No iteration cap** — the loop runs until 0 issues. Do not add a max rounds limit.
- **If the user provides additional instructions** (like "run tests after", "use this pattern", "don't touch file X"), include those constraints in the implementer prompt.
- **Error handling** — if a subagent fails or cannot be resumed, report the error and stop. Exception: specialist reviewer failures are non-fatal (warn and continue); only general reviewer failure is fatal.
- **Every run is multi-reviewer.** Effort 1 is 1 general + simplicity. Individual review files + merge on every run. Simplicity is always in `reviewer_configs`.
- **Include `simplicity` in `run.specializations`** on every memory flush.
- **Severity normalization** — all reviewers use `bug`, `suggestion`, `nit`. The security specialist prompt maps native security severities to this taxonomy.
- **Implementer can push back** — the implementer may set `Status: wontfix` with a technical justification. If a reviewer re-opens a `wontfix`d issue, it's a stalemate → escalate to the user.
- **Escalate, don't spin** — as soon as a reviewer re-opens a `wontfix`d issue, escalate to the user directly. Never let the loop spin on a disagreement.
- **User decisions are final** — once the user resolves a disputed issue, the implementer incorporates it without further debate.
- **Memory is best-effort.** If the `memory.py` helper fails, proceed without it. Never fail a run due to memory issues.
- **Always go through the `memory.py` helper.** Derive `MEMORY_HELPER` from the SKILL.md path (not `$(pwd)`). Never read/write the memory file directly — the helper is the single source of truth.
- **Concurrency-safe writes are the helper's job.** Do not implement your own locking around the helper.
- **Dedup is a two-layer responsibility.** The orchestrator harmonises pattern phrasings against `existing_patterns_snapshot` (Step 6b); the helper does case/whitespace/punctuation normalisation as a safety net.
- **Compaction is automatic.** The helper caps each category at 25 entries and Recent Runs at 20 entries.
- **Assembly rules live in `stack-assembly.md`** — push branch + open 1 PR. Git and worktree safety rules are in `safety-guardrails.md`.
- **Use the `snapshot` subcommand for reads.** `"${PYTHON}" "${MEMORY_HELPER}" snapshot` returns structured JSON. The `read` subcommand is for human inspection only.
- **Briefing is injected, not enforced** — the past-issues briefing is informational context only.
