# Skill Design

You author, improve, and prune agent skill directories (a collection of `SKILL.md` folders). Three modes own three distinct jobs; pick one per invocation.

**Purpose of this skill:** keep the skill tree holding skills that read clean, invoke correctly, follow the shared body shape and lint standard, and carry no duplicate or overlapping folders. `--create` builds from a described job; `--improve` runs the full audit-then-improve sequence on an existing skill (structure, naming, frontmatter, body shape, and dangling refs to the lint standard); `--prune` collapses duplicate or same-purpose skills into one folder.

## Global Rules

Rules that apply to every step. Reference files cite these; they never restate them.

- **Mode scope**: `--create` and `--improve` author/improve a single skill (or pack); `--improve` runs the full audit-then-improve sequence; `--prune` works on a category or the whole tree and collapses overlap. Each mode routes to its own reference; they do not share state.
- **Interface changes ripple**: the `argument-hint` plus every flag and safety-model mention in a skill body must stay in lockstep. Grep the whole skill directory (body and all `references/`) for each flag name and mode term before deciding an edit is done; a flag retired or renamed in `SKILL.md` that still governs a step file silently re-imposes the old behavior for that path. **Safety-model flips** (e.g. flipping the default from interactive-with-approval to headless-autonomous, or inverting when a flag gates execution) touch more than the flag's own mention: every step file that carries a blocking approval step, a "wait for explicit approval" line, a Dry-Run Mode section, a verification checklist item, or a decision-flowchart branch must be found and re-worded to the new semantics. Grep for `approv`, `wait for`, `explicit confirmation`, and the flag name (both bare and backtick-wrapped) across the whole skill directory, not just `SKILL.md`; a step file that still says "wait for approval" under a new headless default silently re-blocks the pipeline for that step.
- **One home per fact.** Each rule, value, or list lives in a single authoritative place — a Global Rules bullet below or a reference file. When an edit touches an existing copy elsewhere, make the requested change and report the duplication instead of silently rewriting.
- **Splitting a language monolith into step variants.** When a Pattern B pipeline skill carries per-language monolith reference files (one file per language bundling multiple phases) and the user asks for `step-<N>[a|b|c]` variant naming: find the phase boundary inside each monolith (usually a `## Phase 2:` heading or equivalent) and split there. The shared preamble (rules, purpose, when-to-use, fundamental questions, language-specific KEEP/REMOVE tables) stays with the first phase's step file; the second phase's step file carries only the phase body plus the cross-phase tails (verification checklists, quick-reference commands, common mistakes, decision flowchart, dry-run mode, tool reference) — those tails span both phases and belong to the later step so the step-1 file stays focused on detection. Re-title each new file to `# Step <N><variant>: <Phase> — <Language>` and add a one-line self-containment note (what the file owns and how it is picked: `picked by target_lang from step 0`). Never leave the old monolith filenames in the tree after the split; delete them (or `git mv` the content out first). **`mkdir -p` any new destination subdirectory before the `git mv` chain** — `git mv` into a not-yet-created subdirectory fails per-file with `fatal: renaming ... failed: No such file or directory`, and a failed first `git mv` aborts the whole chain with no files moved.
- **No no-op sentences.** If a sentence does not change behavior — "be careful", "use best practices", a guardrail restating the instruction it follows — delete it or replace it with a checkable criterion.
- **Solve the class, not the instance.** Fix bad output where the fact is owned, not with a downstream check that catches one symptom. Check every generalization against at least two concrete instances.
- **Set degrees of freedom.** High (text steps) for context-dependent work; medium (parameterized scripts) when a preferred pattern exists; low (exact commands) for fragile, strict-sequence operations.
- **Budget for permanent cost.** `description:` and `when-to-use:` are injected into the skill list every session; the body loads per use; `references/*.md` cost nothing until opened. Keep the two trigger fields non-overlapping, and move anything task-conditional out of the body.
- **Consistent terminology.** One term per concept, no synonyms; model-agnostic wording.
- **Dangling refs rot fast.** `related_skills:`, sibling mentions, and cross-skill links are not existence-checked — resolve each against the tree before relying on it, and remove refs to skills that do not exist.
- **Mandatory frontmatter.** Exactly four keys are mandatory: `name`, `description`, `when-to-use`, `argument-hint`; every other key is optional and target-dependent. Full key table: `references/improve/step-3-frontmatter-keys.md`; validator rule catalog: `references/improve/step-4-validator-catalog.md`.
- **Frontmatter semantics.** `description:` = WHAT + WHEN + trigger terms, third person. Trigger phrases the description cannot fit go in `when-to-use:`, never in a `triggers:` key.
- **YAML hygiene.** Quote values containing `: ` or indicator characters (`{ } [ ] * & # ! | > % @`, backtick); never indent a field under a previous field's value (one nested line invalidates the whole frontmatter — only `name`, `description`, `when-to-use` survive recovery); multi-word keys kebab-case (`when_to_use` is the accepted alias). **Unclosed block**: a `SKILL.md` whose frontmatter opening `---` has no closing `---` (or the closing delimiter was lost) makes the parser treat everything to the first valid end-of-document as one value — `description` and `when-to-use` silently vanish even though the file *reads* fine. An improve pass must verify the second `---` exists *and* sits immediately before the `# Title` heading; `sdc read <skill>` (or the description in the skill list) is the probe — a missing description after a frontmatter edit means the block is not closed, not that the key was dropped.
- **Grok Build parser limits.** `name` ≤ 64 chars; `description` and `when-to-use` ≤ 1,024 chars; top-level `version:`, `triggers:`, and `entry_points:` are ignored.
- **Structure.** Exactly one `SKILL.md` at `<category>/<skill>/SKILL.md` (nested SKILL.md files are rejected). The body is a routing table of contents, ~100–200 lines, with steps that end in checkable completion criteria; detail lives in `references/*.md` (subfolders allowed when the set is large) and every reference, whatever its depth, links directly from `SKILL.md`. Non-trivial logic ships as `scripts/<file>` referenced by path.
- **Tracked catalog artifacts**: `CATALOG.md` and `catalog.json` are both checked-in artifacts at the skills root, regenerated by `sdc skills catalog --build` and drift-verified by `sdc skills catalog --check`. `catalog.json` emits one object per skill with exactly the fields `name`, `description`, `when_to_use`, `category`. Never hand-edit either artifact — always rebuild from the live tree so the two stay in sync.
- **Mandatory body shape.** Every `SKILL.md` uses exactly three sections: `# Title`, `## Global rules`, `## Routing`. All task data, commands, examples, field shapes, stop conditions, and worked examples belong in `references/*.md` or `scripts/*`. If the body contains anything beyond those three sections, move it to a reference before publishing. **Stop conditions, limitations, and "when done" criteria are Global Rules bullets — not their own `##` heading.** A fourth `##` heading (e.g. `## Completion`, `## Current limitations`, `## Pitfalls`) breaks the three-section shape. Before finishing any improve run, grep `^## ` on each target `SKILL.md`: exactly two `##` lines expected, both named `Global rules` and `Routing` (case-insensitive for the first, case-insensitive is acceptable). Any other `##` must be folded into a Global Rules bullet or moved to a reference.
- **Templates are the single source of truth for shape.** `template/template.md` is the entry index; `template/skill.md` is the canonical `SKILL.md` skeleton and `template/reference.md` is the canonical reference-file shape. Every create/improve step copies from the template the index names rather than restating the shape inline; a new artifact kind gets its own `template/<artifact>.md` registered in the index.
- **Audit standard**: `sdc lint` is the mechanical gate; `references/improve/step-0-overview.md` holds the key table, the validator rule catalog, the reference-pattern decision, and the pre-publish checklist. `--improve` runs the full audit-then-improve sequence against that standard and fixes every flagged issue.
- **Validation rules** (enforced when improving, pruning, and consolidating skills): the full rule catalog is `references/improve/step-4-validator-catalog.md`; `sdc lint` is the mechanical gate.
- **Rollback**: the snapshot (or `HEAD` SHA when the tree was dirty) is the undo path; `git reset --hard <sha>` restores both the skill and unrelated state. **A `git reset --hard` also reverts your own tracked-file edits on disk** (untracked new files survive) — after any hard reset, re-verify on-disk state with `git diff` against the target paths and re-apply lost edits before declaring the run done. Record the snapshot SHA in the commit message and final report. A run that cannot commit (snapshot or final commit blocked) falls back to `--dry-run` behavior: report only, no changes applied.
- **Safety model**: every mode runs fully autonomous by default — read-only, edit, snapshot, and execute steps all proceed without asking the user for confirmation. `--dry-run` is the only control flag: it generates the full report and stops before any snapshot or execute, making no changes to the tree. Destructive actions go to `_archive/` first; permanent delete only with explicit `--hard-delete`. **Commit blocked, not `--dry-run`**: when the edit completed and on-disk verification passes but the commit lane is irrecoverably swept by concurrent commits or a dirty tree, the run still ends cleanly — report the on-disk paths as the verified handle, state that the files are uncommitted, and give the exact one-line `git add` + `git commit` command for the quiet-tree retry. Do not fall back to `--dry-run` (report-only) for a run that already applied edits: that would misreport the tree as untouched when it is not.
- **Parallel agents committing in the same tree**: this repo is worked on by multiple agents (GrokBuild via Orca, Hermes). A concurrent commit can sweep your staged changes into someone else's commit and change the HEAD you snapshotted against. The write side races too: a parallel `git checkout`/`reset` can revert a file you already wrote back to its pre-edit content without you noticing (the edit appears in git history but not on disk) — after any batch of writes to a tree other agents also work in, re-read at least one touched file to confirm the new content is on disk before declaring the edit done. After any snapshot and before committing, re-run `git log --oneline -4` and `git status`; re-verify on-disk state before executing; keep your commit scoped to your own task files only — never `git add -A`.
- **Staging discipline**: the index is shared with every parallel agent — `git add <path>` stages your path *plus* everything a concurrent agent already staged, and `git add -A .` inside `skills/<category>/` stages every tracked file under that subdirectory, not just the change's changes. Use explicit top-level paths (`git add skills/<category>/ skills/CATALOG.md`), then verify the staged set with `git diff --cached --name-only` before committing; it will routinely list non-task files. Unstage those with `git reset HEAD -- <each non-task path>` (targeted, never `git reset HEAD -- .` mid-run — that can unstage another agent's work and, if their content is on disk, reverts files to pre-edit state). **Verify after every reset round**: each `git reset HEAD --` printout lists the index state left behind — files an agent staged *after* your last check reappear there; keep looping `add → diff --cached → reset` until the staged set is exactly your task files, then `git commit` (never `-a`, which commits the whole shared index) — after commit, `git show --stat` must list only your files. If you must clear the whole index, re-stage your task files immediately after in the same command chain, then commit; between the clear and the re-stage a parallel agent can re-populate the index and your commit sweeps their files again.
- **A commit is not proof your files landed.** A parallel agent can commit a different change that resets your files on disk, or a `git reset` can unstage them without touching the working tree. Before committing, verify on-disk content (grep the new body shape, list new reference files) — not just that you wrote it earlier. After committing, `git show --stat <sha>` must list only your files; if it lists another task's files or omits yours, the commit is wrong: verify, re-apply via direct writes, re-stage scoped to your task files, commit, then re-verify `git show --stat` on the new SHA. Commit fast while the tree is quiet; the verification round-trip is what defeats the race, not holding the tree. **Variant — your own work was swept into a foreign commit**: if `git log` shows a concurrent agent committed exactly this run's file contents under its own (unrelated, even broken) commit message, do not re-apply or rewrite history — the work is already in the tree under that SHA. Instead: confirm your files are in that commit with `git show --stat <foreign-sha>` (content match by path), check `git status` for any *remaining* uncommitted edits of this run, and commit only the remainder scoped to your task paths. Report both SHAs, note the foreign commit's wrong message, and leave `git reset`/`amend` alone — a history rewrite in a shared tree re-races every parallel agent.
- **Retiring the Orca worktree strands the commit.** `worktree rm` deletes the directory but leaves the Orca branch — the main clone's working tree still shows pre-edit files, and the branch commit SHA is not proof the work landed on the main-clone branch. Land the run in the main clone: `git checkout <orca-branch> -- <task paths>`, re-run the body-shape grep + `sdc lint` on the main clone, then commit scoped to the task paths. Check `git diff --cached --name-only` for non-task files before committing (a stale staged file from another session gets swept in; `git reset <file>` first). The main-clone commit SHA is the verified handle.
